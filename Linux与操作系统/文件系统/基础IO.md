## 系统文件IO

```c
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int open(const char *pathname, int flags);
int open(const char *pathname, int flags, mode_t mode);

int creat(const char *pathname, mode_t mode);

//	pathname: 要打开或创建的目标文件
//	flags: 打开文件时，可以传入多个参数选项，用下面的一个或者多个常量进行“或”运算，构成flags。
//  参数:
//		O_RDONLY: 只读打开
// 		O_WRONLY: 只写打开
//		O_RDWR : 读，写打开
// 		这三个常量，必须指定一个且只能指定一个
//		O_CREAT : 若文件不存在，则创建它。需要使用mode选项，来指明新文件的访问权限
//		O_APPEND: 追加写

//	返回值：
//		成功：新打开的文件描述符
//		失败：-1
```

`open`、`read`、`write`、`close`、`lseek`封装出C语言文件系列接口



### 系统调用和库函数

* 之前提到的，C语言文件系列函数，例如`fopen`、`fclose`、`fread`等，就是库函数（libc，即C语言提供的）
* 而`open`、`read`、`write`、`close`、`lseek`都属于系统提供的接口，即系统调用接口

为什么：系统为隐藏内部功能实现细节，也就是为了保持封装性，避免用户直接使用功能模块，将对外的服务，集成为一系列接口

而之前的C语言文件系列接口其实就是对系统调用的封装



### 文件描述符fd

一个`int`类型的数据，一个哈希模型中的key值

0&1&2：

* Linux进程中默认情况下会有3个缺省打开的文件描述符，分别是标准输入0，标准输出1，标准错误2
* 0，1，2分别对应物理外设一般是：键盘，显示器，显示器

现在知道，文件描述符就是从0开始的小整数。当我们打开文件时，操作系统在内存中要**创建相应的数据结构来描述目标文件**。于是就有了file结构体。表示一个已经打开的文件对象。而进程执行open系统调用，所以**必须让进程和文件关联**起来。**每个进程都有一个指针*files, 指向一张表files_struct**,该表最重要的部分就是包涵一个**指针数组**，每个元素都是一个指向打开文件的指针！所以，本质上，**文件描述符就是该数组的下标**。所以，只要拿着文件描述符，就可以找到对应的文件



#### 分配规则

实验：直接打开新文件查看文件描述符vs先关闭0或者2再打开新文件并查看文件描述符

结果：文件描述符的分配规则是在files_struct数组当中，找到当前没有被使用的最小的一个下标，作为新的文件描述符



#### 重定向

实验：关闭1，写方式打开一个新文件，并使用打印函数打印信息

本来应该输出到显示器上的内容，输出到了新文件当中，其中，fd＝1。这种现象叫做输出重定向。常见的重定向有：`>`， `>>`，`<`

所以重定向的本质：

将原来标准输出的文件描述符的位置改为其他文件，使原来向标准输入传输的数据重定向到其它文件



但是，这样重定向有一个问题，如果想要重定向1，但是0也已经关闭，就要新开一个文件填补0位置的空挡，再将想要1位置重定向的文件打开。以下系统调用解决此问题

##### `dup2`系统调用

```c
#include <unistd.h>

int dup2(int oldfd, int newfd);
// dup2() makes newfd be the copy of oldfd, closing newfd first if necessary, but note the following:
//		*  If oldfd is not a valid file descriptor, then the call fails, and newfd is not closed.
//		*  If  oldfd  is a valid file descriptor, and newfd has the same value as oldfd,
// 		   then dup2() does nothing, and returns newfd.
```



## `FILE`

* 因为IO相关函数与系统调用接口对应，并且库函数封装系统调用，所以本质上，访问文件都是通过fd访问的。
* 所以C库当中的FILE结构体内部，必定封装了fd  



代码实验：

```c
#include <stdio.h>
#include <string.h>
int main()
{
    const char *msg0="hello printf\n";
    const char *msg1="hello fwrite\n";
    const char *msg2="hello write\n";
    
    printf("%s", msg0);
    fwrite(msg1, strlen(msg0), 1, stdout);
    write(1, msg2, strlen(msg2));
    
    fork();
    
    return 0;
}
```

上文提到C语言文件系列接口是对系统接口做了封装，对文件的属性进行了描述，其中就包括了**缓冲区**属性

实验结果：

* 直接运行

  ```
  hello printf
  hello fwrite
  hello write
  ```

* 将输出重定向至文件中，`./hello > text`

  ```
  hello write
  hello printf
  hello fwrite
  hello printf
  hello fwrite
  ```



原因或者说这个实验说明

* C语言文件系列库函数是有缓冲区策略的
* 对文件的写入的是全缓冲，而显示器则是行缓冲
* fork之后缓冲区的数据也被拷贝，直到进程退出才完成写入

具体文件结构体中的内容可以看

* `typedef struct _IO_FILE FILE;`
* 在`/usr/include/stdio.h`

当然，为了提升整机性能，OS也会提供相关内核级缓冲区

这些信息是什么？



如何管理本地外存设备的空间？是什么？为什么？怎么做？

将外存抽象成数组，按区块分组层级管理（也就是外存需要提供随机访问以及随机存取的机制）



以ext2文件系统为例，看看是如何管理本地外存设备的空间的

* BootBlock
* BlockGroup1~BlockGroupN



ext2文件系统会根据分区的大小划分为数个Block Group。而每个Block Group都有着相同的结构组成：

* 超级块（Super Block）：存放文件系统本身的结构信息。记录的信息主要有：bolck 和 inode的总量，未使用的block和inode的数量，一个block和inode的大小，最近一次挂载的时间，最近一次写入数据的时间，最近一次检验磁盘的时间等其他文件系统的相关信息。Super Block的信息被破坏，可以说整个文件系统结构就被破坏了  
* GDT（Group Descriptor Table）：块组描述符，描述块组属性信息，比如块组中空闲块和inode的数目等，每个块组都包含文件系统中**所有块组的组描述信息**
* 块位图（Block Bitmap）：Block Bitmap中记录着Data Block中哪个数据块已经被占用，哪个数据块没有被占用  
* inode位图（inode Bitmap）：每个bit表示一个inode是否空闲可用
* i节点表（inode Table）：存放文件属性 如 文件大小，所有者，最近修改时间等
* 数据区（Data Block）：存放文件内容



**超级块和块组描述符是全局信息**

* 这两块数据都采用冗余策略，如果系统崩溃破坏了超级块或者块组描述符，有冗余的副本就有恢复可能
* 通过使文件和其管理数据尽可能接近，减少磁头寻道和旋转（对于其他需要提供随机存取机制的外存设备也是如此），提高文件系统的性能

后续版本也采用了稀疏技术，超级块和块组描述符存在块组0、块组1和其他ID可以表示为3、5、7的幂的块组，以减少副本更新消耗



数据区是被切分成块的，以创建文件为例

1. 存储属性

   内核先找一个空闲的inode节点（inode Bitmap中找，存储位置在inode Table），并将文件信息记录到其中

2. 存储数据

   若该文件需要3个数据块，内核找到3个空闲块（从Block Bitmap中找）然后将内核缓冲区中的数据按块大小依次装填

3. 记录分配情况

   文件内容按顺序在200，300，500（例）存放，内核在inode上的磁盘分布区记录上述块列表

4. 添加文件名到目录

   新的文件名test（例）。linux如何在当前的目录中记录这个文件？内核将需要的文件属性（inode编号和文件名）添加到目录文件（目录就是文件）。通过文件名找inode编号，再通过inode找文件信息和文件内容。而这也持久化存储了目录树形结构



那平时命令行上看到的文件是什么呢？**目录项**

目录项，也就是dentry，用来记录文件的名字、索引节点指针以及与其他目录项的层级关联关系。多个目录项关联起来，就会形成目录结构，但它与索引节点不同的是，**目录项是由内核维护的一个数据结构，不存放于磁盘，而是缓存在内存**。目录项这个数据结构不只是表示目录文件，也可以表示其他普通文件。

如果查询目录频繁从磁盘读，效率会很低，所以内核会把已经读过的目录用目录项这个数据结构缓存在内存，下次再次读到相同的目录时，只需从内存读就可以，大大提高了文件系统的效率。



### 硬链接

真正找到磁盘上文件的并不是文件名，而是inode。 其实在linux中可以让**多个文件名（或者说目录项）对应于同一个inode**

```
[crush@VM-8-12-centos test]$ ln fork_t tt
[crush@VM-8-12-centos test]$ ls -1li
total 28
655845 -rwxr-xr-x 2 crush crush 9056 Aug 17 20:27 fork_t
655817 -rw-rw-r-- 1 crush crush  239 Aug 17 20:27 test.cc
655845 -rwxr-xr-x 2 crush crush 9056 Aug 17 20:27 tt
```

* fork_t和tt的链接状态完全相同，他们被称为指向文件的硬链接。内核记录了这个连接数，inode655845 的硬连接数为2
* 我们在删除文件时干了两件事情：1.在目录中将对应的记录删除，2.将硬连接数-1，如果为0，则将对应的磁盘释放
* 每个文件系统都有各自的inode数据结构和列表，所以**硬链接不可用于跨越文件系统**



### 软链接

相当于重新创建了一个文件，**有独立的inode，但是文件的内容是另一个文件的路径**，所以访问软链接实际上相当于访问另一个文件，所以**软链接是可以跨文件系统**的，甚至**目标文件被删除，链接文件还是会存在**，只不过会找不到指向的文件，当然如果在指向路径重新创建一个同名的新文件，此软链接也会同样指向该文件

```
[crush@VM-8-12-centos test]$ ln -s a.out  tt
[crush@VM-8-12-centos test]$ ll
total 16
-rwxr-xr-x 1 crush crush 9112 Aug 22 00:11 a.out
-rw-rw-r-- 1 crush crush  384 Aug 22 00:11 test.cc
lrwxrwxrwx 1 crush crush    5 Aug 22 18:03 tt -> a.out
```



### 文件的使用（IO）

对于操作系统中大量进程打开的文件，必然是需要管理起来的，而管理必然要设计使用特定的数据结构，简单讲几条属性以及对应的管理策略

* 一个文件是可以被多个进程打开的，所以其关系必然不可能是1对1的，所以使用**文件打开计数器**记录该文件被打开次数，当计数器为0时，关闭文件，将缓冲区所有数据刷新到外存（磁盘）

* **缓冲区**，这个缓冲区就是**系统级**的了，为了提到与外存IO的效率，并且系统和磁盘通常都是以数据块为单位操作的（通常是4KB），当然操作系统也有提供**`fsync`**函数，调用此函数时强制刷新该文件的缓冲区，通常是为了确保数据不会因系统崩溃而丢失时，每次写入都强制刷新

  ```c
  #include <unistd.h>
  
  int fsync(int fd);
  ```

  （未验证）这个缓冲区可能是抽象出来的，可能是被加载到内存中的对应数据块，或者新的数据块

* 文件指针，追踪读写位置，对于打开文件的某个进程是唯一的（即跟进程对应）

* 文件磁盘位置（？？？）：绝大多数文件操作都要求操作系统修改文件数据，这些修改后的版本是保存在内存中的，避免每个操作都从磁盘读取（是否在缓冲区中？或者说缓冲区就是被加载到内存中的对应数据块）
也就是磁盘文件的IO以块为单位，或者说**文件系统的基本操作单位为数据块**

### 目录的存储

目录也是文件（甚至可以用`vim`打开），也有inode，inode里面也指向一些块，和普通文件不同的是，普通文件的块保存的是文件内容（格式化数据），而**目录文件的块里面保存的是目录里一项一项的文件信息**（其实也是格式化数据，这是针对目录的格式化数据）

目录文件的块中，最简单的保存格式就是列表，就是一项一项地讲目录下的文件信息（如文件名、文件inode、文件类型等）列在表里

通常第一项时`.`，表示当前目录，第二项是`..`，表示上一级目录

如果一个目录有超级多文件，线性找文件的效率就不高了。于是保存目录的格式改成了哈希表，对文件名进行哈希计算（ext文件系统就采用的是哈希表）

目录查询通常需要反复搜索，不断进行IO，开销较大。为了减少开销，通常会将当前使用目录缓存到内存中
